# ProofFlow 从当前版本到最终演示的实施路线图

更新日期：2026-10-03
适用范围：成员三（Backend / Provenance Engine）与成员一（Product Lead / Integration / Pitch）由同一人负责的情况。

> 目标不是一次做完原分工表里的所有功能，而是先交付一条可运行、可验证、可诚实解释的演示流程。

## 0. 当前基线与边界

当前 `main` 已有自研 JSON 编辑器、文档创建和读取、`MANUAL_EDIT` / `PASTE` / `AI_INSERT` 事件保存、SQLite 持久化、FIFO 保存队列、版本冲突检查、操作 ID 去重、插入内容校验以及 SHA-256 事件哈希链。新事件已采用可复算的 v1 证据格式；旧事件仍为 v0，不能直接签发 v1 证书。现有前端的 AI 回答是服务器记录的固定示例，不是真实 LLM 调用。

**尚未完成：**Finalize、证书表、数字签名、独立 Verify、证据包导出、登录和文档权限、适合公网的共享数据库。证书按钮目前禁用。成员四的 Python 文件监听器与网页事件链是两套流程，哈希格式也不同，不能直接称为已经集成。

相关代码和说明：

- `frontend/lib/server/provenance.ts`：SQLite 表、保存事件、读取并检查可签发证据。
- `frontend/lib/proof-format.ts`：v1 规范化 JSON、哈希和证书签名字节。
- `frontend/tests/proof-format.test.mjs`：包含中文、emoji、空值和键顺序的黄金测试向量。
- `frontend/app/ProofFlowEditor.tsx`：编辑器、FIFO 保存队列、禁用的证书按钮。
- `frontend/app/api/documents/`：现有文档和事件路由。
- `frontend/tests/api.integration.test.mjs`：现有 API 集成测试。
- `frontend/tests/ui.smoke.test.mjs`：现有 UI 冒烟测试。
- `docs/backend-contract.md`：现有数据契约和 v1 证据、证书格式。
- `frontend/README.md`：启动方法和已知限制。

**能力边界：**浏览器记录的事件类型是对操作的记录，不是“人类创作证明”；哈希链可以检测指定证据的改动，但未签名或未固定公钥的链无法抵抗有权重写整套数据的管理员。签名也不等于第三方可信时间戳。

## 1. 锁定 MVP 演示与负责人

建议把最终演示固定为：

1. 新建文档，进行手动编辑。
2. 粘贴文本，时间线显示 `PASTE`，正文可定位对应内容。
3. 插入一条已记录的 AI 回答，时间线显示 `AI_INSERT`。
4. 等待全部事件保存，Finalize 文档并生成证书。
5. 导出证据包，Verify 显示 `VALID`。
6. 修改证据包中的一个字或一个事件，再验证显示 `INVALID`。

负责人建议：

| 工作 | 负责人 |
| --- | --- |
| 契约、数据库、Finalize/证书/Verify API、集成、测试、部署、答辩 | 你（成员一 + 三） |
| 证书按钮、证书页、验证页、保存失败提示 | 成员二 |
| 签名/验签规则、AI 回答接入；或与你共同实现验证模块 | 成员四 |

**需团队确认：**评委必须访问公网网址，还是可以在同一台电脑现场演示？真实 LLM 是否为比赛硬性要求？这两个答案决定后续工作量。网页 `documents/events` 应作为本次证据链的唯一正式数据来源；Python 文件监听器暂时单独展示，不把文件变化硬映射为网页编辑事件。

**完成标准：**团队认可同一条演示流程、接口负责人和不做的内容。

## 2. 固定证书与证据包契约

复核 `docs/backend-contract.md` 已定义的证书版本 1 字段，并以此作为签发和验证的共同契约：

```json
{
  "certificateId": "<uuid>",
  "documentId": "<uuid>",
  "finalVersion": 4,
  "finalizedAt": "<server ISO timestamp>",
  "contentHash": "<sha256 hex>",
  "eventCount": 4,
  "eventHeadHash": "<sha256 hex>",
  "hashFormatVersion": 1,
  "keyId": "<signing key identifier>",
  "signature": "<base64 signature>"
}
```

这些字段已有格式定义，但当前还没有证书签发 API 或实际返回。证据包还应包含最终 `contentJson`、按版本排序的完整事件及该证书。不要仅凭 `certificateId` 查询数据库后返回“有效”；验证者必须能从证据包重算正文哈希和整条事件链，再验证签名。

`frontend/lib/proof-format.ts` 已实现规范化 JSON、正文及事件哈希和证书签名字节；`provenance.ts` 已保存完整规范化事件负载，并提供 `readSignableEvidence()` 检查版本连续性、哈希链及最终正文一致性。旧事件缺少可复算的 v1 负载，不能直接签发 v1 证书。已有包含中文、emoji、空值和不同键顺序的黄金测试向量。实施 Verify 时应复用同一字节规则，补齐独立验证模块和篡改测试；如果成员四使用 Python 验证，须用同一向量跨语言比对。

签名可使用 Node `node:crypto` 支持的 Ed25519。私钥只放服务器环境配置，不提交 Git、不发给浏览器；公钥及其指纹应固定并供验证方获取。验证时不能无条件相信被验证包自行提供的公钥，否则攻击者可以同时替换证据、签名和公钥。

**完成标准：**同一份证据每次得到相同哈希；改正文、事件、顺序或签名，验证都会失败。

## 3. 实现数据库冻结与 Finalize API

在现有数据层增加 `certificates` 表，至少存证书 ID、文档 ID（唯一）、最终版本、正文哈希、事件链头、签发时间、格式版本、签名及密钥 ID。现有 `documents.status` 可从 `draft` 切换为 `finalized`；Finalize 后现有保存接口应继续拒绝新增事件。

建议接口：

```http
POST /api/documents/:documentId/finalize
Content-Type: application/json

{ "expectedVersion": 4 }
```

后端在一个事务内执行：

1. 检查文档存在、仍为 `draft`，且 `expectedVersion` 等于服务器当前版本。
2. 检查事件版本从 1 到最终版本连续，最后事件正文与当前文档正文一致。
3. 用服务器数据计算正文哈希与事件链头；不要使用浏览器提交的“最终正文哈希”作为事实。
4. 签发证书，插入唯一证书记录，将文档状态更新为 `finalized`；失败则整体回滚。
5. 对重复请求返回同一证书或稳定的冲突结果，绝不生成第二份不同证书。

**完成标准：**旧版本请求返回 `409`；成功后不可再编辑；重复请求不增加证书；签名或数据库出错不留下半份证书。版本 0 的空文档能否 Finalize，也要在契约里明确规定。

## 4. 实现独立 Verify 与证据包导出

建议提供以下能力，具体路径可在第 2 步定稿：

| 能力 | 建议路径 | 作用 |
| --- | --- | --- |
| 读取证书 | `GET /api/certificates/:certificateId` | 展示签发结果 |
| 导出证据包 | `GET /api/certificates/:certificateId/bundle` | 获取证书、最终正文和完整事件 |
| 验证证据包 | `POST /api/verify` | 返回 `VALID` 或 `INVALID` 及原因 |

核心验证逻辑应做成不依赖数据库的纯函数：检查证据包格式与事件版本连续性，逐条重算事件哈希，重算最终正文哈希，对照证书中的 `eventHeadHash` / `contentHash`，最后用预先信任的公钥验签。API 和上传证据的页面都调用同一套规则。若只对数据库中现有记录做查询，不能称为独立验证。

**完成标准：**原始证据包为 `VALID`；正文改一个字、删事件、调换事件、修改签名均为 `INVALID`，且给出清楚但不泄露敏感数据的原因。

## 5. 接通前端的“保存完再签发”流程

与成员二一起把 `ProofFlowEditor.tsx` 的禁用证书按钮接通。按钮处理必须依次做到：

1. 暂停新编辑，让当前输入结束并产生待保存事件。
2. 等待 FIFO 队列逐条获得服务器成功响应；不能仅凭 React 状态显示“已保存”。
3. 队列为空后重新确认服务器版本与已确认版本一致，再调用 Finalize。
4. 任一保存失败、版本冲突或 Finalize 失败，停止签发并显示可恢复错误。
5. 签发成功后进入只读状态，显示证书、证据包下载和 Verify 入口。

当前手动输入每次变化都生成事件，尚无防抖。先保证保存与签发的正确顺序，再决定是否合并输入事件。不能通过固定等待几秒来推测保存已经结束。

**完成标准：**快速输入后立刻点击证书，证书仍包含最后一次编辑；断网或保存失败时绝不签发旧版本；刷新后仍能看到最终状态。

## 6. 决定真实 AI 和部署分支

**AI：**当前回答是服务器记录的固定示例。若比赛要求真实 LLM，成员四需提供“生成回答并在服务器持久化”的接口，再让 `AI_INSERT.aiResponseId` 指向该记录，并校验插入文本与记录一致。若不要求真实 LLM，可以保留示例，但 UI 与答辩须明确说“模拟 AI 回答”。

**现场同机演示：**继续使用 SQLite，服务仅绑定 `127.0.0.1`；不存真实私人文稿。备份演示数据库并录制完整流程的视频。

**公网演示：**先确定托管平台和共享数据库，将 SQLite 事务语义迁移到共享数据库，加入登录、文档所有权校验、访问限制和速率限制，然后再开放服务。不能把当前无鉴权 API 直接暴露公网。若选择 Supabase，服务端密钥不能进入前端，还需正确配置 grants 和 RLS。Next.js 应作为 Node 服务或适配平台部署，不是仅导出静态网页。

**完成标准：**部署方式与真实能力一致；不会因多实例、临时文件系统或未授权访问而丢失/泄露证据。

## 7. 测试、PR 与合并

后端集成测试至少覆盖：正常保存后 Finalize、旧版本 Finalize、重复 Finalize、Finalize 后保存事件、证据包导出、正常 Verify、四种篡改失败。UI 冒烟测试至少覆盖：快速输入后立即签发、保存失败时禁止签发、签发后只读、验证有效和无效的界面状态。签名密钥使用专用测试密钥；不要把实际私钥提交仓库。

从 `frontend/` 运行：

```powershell
npm test
npm run lint
npm run build
npm run dev -- -p 3001 -H 127.0.0.1
```

服务启动后，在另一个终端运行：

```powershell
npm run test:integration
npm run test:ui
```

按功能在分支开发、通过 PR 合入 `main`。合并前检查工作区、测试和预览；不要把 `frontend/data/proofflow.sqlite`、真实密钥、个人数据或录屏原件误提交。最后更新 `frontend/README.md`、`docs/backend-contract.md` 和示例请求，核对文档描述与实际接口、密钥配置和部署方式一致。

**完成标准：**所有测试通过；一台全新环境按 README 能启动并复现完整 Demo；`main` 与展示版本一致。

## 8. 演示与答辩收尾

准备一份简短讲解稿、架构图、可复现的演示数据和备用视频。现场严格按照第 1 步的流程操作，重点让评委看到“有效”与“篡改后无效”的区别。讲解中明确区分：

- **已实现：**记录编辑操作、保存结构化正文、按版本关联事件、冻结最终版本、对证据完整性进行验证。
- **不能证明：**操作者一定是人、文本完全没有受外部 AI 影响、服务器时间已由第三方公证、私钥永不泄露。
