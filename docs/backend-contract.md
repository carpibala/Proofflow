# ProofFlow editor and backend contract (historical draft)

> **历史设计稿，已不再作为当前实现契约。** 团队已取消 AI、证书、数字签名和公钥计划。冻结与无签名证据包的现行接口见 [当前证据契约](current-evidence-contract.md)。下文仅保留早期讨论记录，请勿据此实现或答辩。

Status (2026-10-04): a local Next.js + SQLite demo implements the custom JSON editor, `documents`/`events` API, FIFO event saving, optimistic versions, idempotency, insertion validation, and a SHA-256 event chain. The Records view lists and filters server-saved events, counts changes and `PASTE` operations, and calls `GET /api/documents/:documentId/verify` for internal chain/content verification. A pure verifier also accepts an optional trusted external head hash. New events use the reproducible v1 evidence format below. Certificate and evidence types plus signing bytes are defined, but Finalize, signature issuance, evidence export, and signature verification are not implemented. The service is unauthenticated and must stay local until access control is added.

This contract describes the first vertical slice: create a document, save one edit, read it back, and show the saved event. The editor is a custom React editor; the JSON shape below is a ProofFlow format, not a Tiptap or Slate format.

## Decisions proposed for the first slice

| Topic | Proposed rule |
| --- | --- |
| Content format | `proof-flow-json` with `editorSchemaVersion: 1` outside `contentJson` |
| Root node | `{ "type": "doc", "content": [...] }` |
| Children | `doc` contains `paragraph` nodes; a `paragraph` contains `text` nodes |
| Text | `{ "type": "text", "text": "..." }`; optional `marks: [{ "type": "bold" }]` and `sourceOperationId` |
| Empty document | One paragraph with an empty `content` array |
| Save version | Server-owned integer, starting at `0` and increasing by one for each accepted edit |
| Operation ID | Frontend generates a UUID with `crypto.randomUUID()` and reuses it on retry |
| IDs | Backend creates and returns a document UUID; events use server IDs; member 4's AI response ID format remains open |
| Time | Server stores `receivedAt`; client `event.timestamp` is optional and is not trusted as server time |

The older editor state was an array of `{ "type": "paragraph", "content": "..." }` objects; see `docs/examples/current-editor-state.json` for that historical snapshot. The current editor exports `contentJson` with `doc` / `paragraph` / `text` nodes and saves it through the API. Schema version remains outside `contentJson`; `baseVersion` and server `version` describe save history.

Document examples are in `docs/examples/empty-document.json`, `plain-paragraph.json`, and `formatted-paragraph.json`. Member 2's earlier illustrative `PASTE` payload is preserved in `docs/examples/save-paste.request.json`; its old IDs are not generated by the current code. `docs/examples/paste-before.json` and `save-paste.target.request.json` describe the target request shape. The current editor can export actual JSON from the header action.

## Event types

| Type | Meaning | Required extra information |
| --- | --- | --- |
| `MANUAL_EDIT` | Confirmed edit made inside the editor | None for the first slice |
| `PASTE` | Paste action observed by the editor | `insertedText`, `insertPosition: { path, offset }`; optional `snippet` is a timeline preview |
| `AI_INSERT` | User inserted content from an in-product AI response | `aiResponseId` plus the actual adopted text or fragment |

The current page emits `MANUAL_EDIT` and `PASTE`; the backend still supports `AI_INSERT` for existing records and API clients, but the AI assistant control has been removed from the page. A browser event type is a claim about the action, not independent proof of human authorship. For `PASTE`, `aiResponseId` is omitted or null. `snippet` is only a preview; `insertedText` is full text. `insertPosition.path` indexes the pre-event paragraph, and `offset` counts UTF-16 code units. Optional `replacedLength` covers selection replacement. The local implementation also supports multi-paragraph paste by splitting on newlines. Text nodes carry `sourceOperationId` for surviving sourced spans; later manual edits split nodes without attributing newly typed text to the old operation. The server replays paste/AI insertion and compares the resulting JSON.

For `AI_INSERT`, the server must check the referenced response against a server-side response record owned by the user/document. The AI response storage and ID format need agreement with member 4.

For the first slice, each accepted event stores the full `contentJson` after the operation (`contentAfter`). This supports simple history replay for short demo documents. Format validation must limit accepted node types, marks, nesting depth, and request size; the exact limits and editor extensions need member 2's confirmation.

## API proposal

Authentication target: these routes must require a signed-in user, with actor and owner derived from the session. The current local demo has **no authentication** and must not be deployed publicly. The team must confirm its authentication provider and database ownership model.

### Create: `POST /api/documents`

Request:

```json
{
  "title": "AI in the classroom",
  "editorSchemaVersion": 1,
  "contentJson": { "type": "doc", "content": [{ "type": "paragraph", "content": [] }] }
}
```

Response (`201`; the ID value is illustrative until ID format is agreed):

```json
{
  "id": "a0a8bcbd-70ca-47b4-b02a-acf9acbfdf82",
  "title": "AI in the classroom",
  "editorSchemaVersion": 1,
  "version": 0,
  "status": "draft"
}
```

### Read: `GET /api/documents/:documentId`

Response (`200`): document `id`, `title`, `editorSchemaVersion`, current `contentJson`, `version`, and `status`. The current editor must be able to load `contentJson` without dropping supported marks or nodes.

### Save: `POST /api/documents/:documentId/events`

A valid independent manual request is in `docs/examples/save-manual-edit.request.json`; the agreed target paste shape is in `docs/examples/save-paste.target.request.json`. The route carries `documentId` in the URL and the body repeats it; the server rejects a mismatch. `baseVersion` is a top-level request field, outside `contentJson`. The body also carries `event.operationId`, `event.type`, optional `event.timestamp`, optional `event.aiResponseId`, optional `event.snippet`, `PASTE` fields `event.insertedText` and `event.insertPosition`, and the complete `contentJson` after the operation. If `editorSchemaVersion` is supplied, it must match the document's stored schema version; otherwise the server uses the stored value.

Member 2's earlier paste example has `baseVersion: 3`, so a successful first save would return version `4`. Its `op_1727938200000` value was illustrative and is not the current page's generated format. The current page uses `crypto.randomUUID()` for operation IDs. Treat operation IDs as opaque and do not derive event time from them.

Response (`201`):

```json
{
  "documentId": "a0a8bcbd-70ca-47b4-b02a-acf9acbfdf82",
  "eventId": "9e59e676-4715-4ab7-bfd0-2225e6ca1427",
  "operationId": "69921d50-563e-4842-a68e-6bb450905f5d",
  "version": 1,
  "saved": true
}
```

Save rules:

1. Check authentication, ownership, document status, stored editor schema version, JSON shape, and matching document IDs when both route and body contain one.
2. Check whether this `operationId` has already been accepted for this document. Identical retry returns the previous event and version; reuse with a different payload is a conflict.
3. Check `baseVersion` against the document's current server version. A new operation based on an old version returns `409`.
4. In one database transaction, insert the event with the next version and update the current document JSON/version. A failure must leave both unchanged.
5. Return `saved: true` only after the transaction commits. The frontend uses the returned version for its next operation.

Expected errors: `400` malformed request; `401` unauthenticated; `403` unauthorized; `404` missing document; `409` stale version or conflicting operation ID; `422` unsupported editor JSON. The team should agree whether unauthorized document IDs are reported as `403` or `404` without exposing private documents.

The current frontend queues edits FIFO per document, reuses `operationId` on retry, and uses each save acknowledgment's version as the next `baseVersion`. It groups manual input into one event when punctuation or a newline is inserted, on blur, or after about two seconds of inactivity. Text being typed remains in the local draft until that event is queued and acknowledged. The report button flushes pending input and waits for saved events before navigating to an unsigned verification report. Finalize is still unimplemented; it must check the expected server version and freeze a consistent document/event range before issuing a certificate.

## Evidence and certificate format v1

This is the format for **newly saved events**. `hashFormatVersion` is `1`. Existing database rows are marked version `0` after migration because their raw optional `event` fields were not retained. They must not be issued a v1 certificate. For the local demo, use a newly created document; migrating old rows requires a separately specified legacy verifier or a deliberate reset, not an assumed rehash.

The exported package will have this shape:

```json
{
  "formatVersion": 1,
  "certificate": {
    "certificateId": "UUID",
    "documentId": "UUID",
    "finalVersion": 1,
    "finalizedAt": "2026-10-03T00:00:01.000Z",
    "contentHash": "64 lowercase hex characters",
    "eventCount": 1,
    "eventHeadHash": "64 lowercase hex characters",
    "hashFormatVersion": 1,
    "keyId": "ed25519-sha256:<64 lowercase hex characters>",
    "signature": "base64url without padding"
  },
  "contentJson": { "type": "doc", "content": [{ "type": "paragraph", "content": [] }] },
  "events": []
}
```

The example values illustrate field types, not a valid package. A real package contains every event from version `1` through `finalVersion` in order. Each event has exactly `eventId`, `documentId`, `version`, `event`, `receivedAt`, `contentAfter`, `previousHash`, and `eventHash`. The nested `event` has exactly `operationId`, `type`, `timestamp`, `snippet`, `aiResponseId`, `insertedText`, `insertPosition`, and `replacedLength`. Missing optional input fields become explicit `null`; `insertPosition` is `null` or `{ "path": [0], "offset": 0 }`. The signer stores this complete normalized nested object in `events.event_payload_json`, so it never needs to infer omission from split SQLite columns. For an empty version-0 document, `events` is empty, `eventCount` is `0`, and `eventHeadHash` is 64 zeroes.

Canonical JSON accepts only JSON values: `null`, boolean, finite number, string, array, and plain object. It sorts object keys recursively by JavaScript UTF-16 code-unit order; arrays retain order; strings and finite numbers use `JSON.stringify` spelling. There is no whitespace between tokens. `undefined`, non-finite numbers, and non-JSON objects are rejected. Every hash below uses UTF-8 bytes of the given prefix plus canonical JSON, and SHA-256 produces lowercase hex:

```text
contentHash = SHA256_UTF8("ProofFlow content v1\n" + canonical(contentJson))
eventHash   = SHA256_UTF8("ProofFlow event v1\n" + canonical({
  previousHash, documentId, version, eventId, event, receivedAt,
  contentJson: contentAfter
}))
```

The first event's `previousHash` is 64 zeroes. Later events use the previous `eventHash`. Certificate signing bytes are UTF-8 of `"ProofFlow certificate v1\n" + canonical(certificate fields except signature)`. All nine unsigned fields shown above are covered. Use Ed25519 one-shot signing over those bytes; encode the result as unpadded base64url. `keyId` is `ed25519-sha256:` plus lowercase SHA-256 hex of the public key's DER SPKI bytes. The private key stays in server environment configuration. The verifier needs a public key or its fingerprint from a trusted channel independent of the uploaded evidence package.

Golden v1 example: a one-event `MANUAL_EDIT` of `中文 😀`, with document ID `11111111-1111-4111-8111-111111111111`, event ID `22222222-2222-4222-8222-222222222222`, operation ID `33333333-3333-4333-8333-333333333333`, `receivedAt` `2026-10-03T00:00:00.000Z`, `snippet` `中文 😀`, all other optional event fields `null`, and `contentAfter` equal to a `doc` with one paragraph and one text node containing `中文 😀`, yields:

```text
contentHash = ea47080ed6c8845e3e80208c5d6c59882ec64b05555e48914957a77c1ecee0b2
eventHash   = 353adb19ad090c6e79bfad433478f6a03de0fb3e4290702ca2391ceef9fc3be2
```

The signer-side implementation is in `frontend/lib/proof-format.ts`; `readSignableEvidence(connection, id)` in `frontend/lib/server/provenance.ts` assembles the complete v1 data and rejects gaps, broken hashes, inconsistent event metadata, legacy rows, or a final document that differs from the last event. `verifyEvidenceChain(evidence, expectedHeadHash?)` is a database-independent function; the optional head must come from a trusted channel. `GET /api/documents/:documentId/verify` calls this internal verifier and reports whether the local rows are self-consistent, not whether a signature or external anchor is valid. Finalize must call `readSignableEvidence` inside its freeze transaction. The current `request_hash` is for save idempotency; it is not part of this evidence digest. An `AI_INSERT` event binds its inserted text and response ID, but this v1 package alone does not independently prove that a model generated that response. Browser action labels likewise do not prove human authorship or provide a trusted timestamp.

## Integration acceptance check

1. Create a document and receive version `0`.
2. Save one `MANUAL_EDIT` with `baseVersion: 0`; receive version `1`.
3. Reload the document; its JSON and version match the save response.
4. Read the event list; it contains that operation once and its `contentAfter` matches the document.
5. Retry the same operation ID and payload; no second event appears.
6. Send a new operation with stale `baseVersion: 0`; receive `409` without changing the document.
7. For the target paste example, insert `event.insertedText` at the stated pre-event paragraph position; the resulting paragraph text and `sourceOperationId` match `contentJson`.
