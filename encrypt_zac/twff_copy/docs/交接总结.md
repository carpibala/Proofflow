## 一、这是什么

一句话：**监视一个文件，每次内容变化就记一条带哈希链的事件，事后可验证没被篡改。**

```
textfile.txt 变化 → 记录事件（改在哪、增删多少、删了什么、加了什么）→ 串进 SHA-256 哈希链
```

| 项目 | 值 |
|---|---|
| 主程序 | [`../chainlog.py`](../chainlog.py)（约 33 KB，纯标准库，无第三方依赖） |
| 子命令 | `init` / `watch` / `announce` / `verify` / `show` |
| 运行环境 | Python 3.11+（实测 3.11 / 3.12），Windows |
| 记录格式 | 与 TWFF `meta/process-log.json` 兼容 |
| 测试 | [`../test_diff.py`](../test_diff.py)（29 项，全过）+ [`../tests/5kb/`](../tests/5kb/README.md)（实测三档全过） |

**它不做什么**：不做 AI 检测、不记录"谁"改的、不加密、不联网。

**TWFF 仓库在本目录之外。** 本构件自包含、可独立运行，只有"跨实现校验"那一步需要它。
常见位置：`..\twff\`（即 `encrypt_zac\twff`）或 `D:\hacku\teamproject\zacc\encrypt_zac\twff`。
两处都可能带 `.git`，`git pull` 即可更新。

## 三、快速上手（30 秒）

```powershell
cd D:\hacku\teamproject\Proofflow\encrypt_zac\twff_copy

# 终端提示符有 (mytest) 就说明环境已激活
python chainlog.py init  --file textfile.txt --log audit.json

# 另开一个窗口改文件；这个窗口会被监视占住，Ctrl+C 结束
python chainlog.py watch --file textfile.txt --log audit.json --interval 1.0

# 结束后
python chainlog.py announce --log audit.json --out anchor.json   # 固化链外锚点
python chainlog.py verify   --log audit.json --file textfile.txt # 复算链 + 比对正文
python chainlog.py show     --log audit.json                     # 看时间线
```

> ⚠️ **不要用 `$PY` 之类的变量**。用户踩过一次：忘了赋值就报
> 「&后面的表达式生成无效的对象」。直接用 `python`。

## 四、实现期踩过的坑（最有价值的部分）

这些坑都已修复并有测试覆盖，**但同类问题很容易重犯**，所以逐条记下来。

### 1. 哈希输入用 `ensure_ascii=False` → 与其他实现无法互验

`compute_event_hash()` 里 `json.dumps` 必须用**默认的 `ensure_ascii=True`**。
最初写成 `False`，中文预览被存成原字符而非 `\uXXXX`，导致**同一条事件算出两个哈希**，
twff 自带校验器直接 FAIL。

**结论：哈希输入必须 ASCII 稳定。**（`compute_event_hash()` 的 docstring 里写了原因。）

### 2. `diff_fragments()` 返回值解包顺序反了 → 删除/新增完全颠倒

函数返回 `(removed, added, truncated)`，接收端却按 `(added, removed)` 解包。
表现：每个事件的"删除"和"新增"互换，**看起来完全合理**，只有对照编辑历史才能发现。

**结论：多返回值一定要在 docstring 里写明顺序**（已写），并有单测钉住。

### 3. 为"保证哈希只含 ASCII"而削掉中文 → 中文全丢

修问题 1 时矫枉过正：把预览里 `ord(ch) >= 128` 的字符全替换成 `?`，
于是**中文一个字都记不下来**。

**结论：不要用削掉内容的方式去换哈希稳定。** `ensure_ascii=True` 已经解决了转义歧义。

### 4. stdout 块缓冲 → "只有结束终端才写入"

`print` 在输出被重定向/管道捕获时走 4–8 KB 块缓冲，事件少就一直攒着。
修法：启动时 `stream.reconfigure(line_buffering=True, encoding="utf-8")`，
且**先落盘、再打印**、每条 `flush()`。

**结论：这类"看起来是逻辑问题、实际是 IO 缓冲"的 bug，验证方式必须是
"进程仍在运行时读它的输出文件"。**

### 5. 截断只留尾部 → 看不到改动落在哪

超长片段最初只截尾部。对"改动在哪里"这个核心问题，尾部截断等于把信息丢了。
改成**首尾保留、中间省略**。

### 6. `os.kill(pid, 0)` 判断存活 → 锁守卫失效

原以为对不存在的 pid 会抛 `ProcessLookupError`。实测在受限环境里，
对**存活的外部进程**它也会抛 `OSError WinError 87`。
所以 **WinError 87 ≠ 进程不存在**，只是"探测不了"。

修法：`pid_alive()` 返回三态 `True / False / None`，只有明确的
`ProcessLookupError` 才判死，其余回落到**锁心跳新鲜度**（watch 每 30 s touch 锁）。

**结论：宁可拦住一次操作，也不要静默覆盖别人的数据。**

### 7. 差点造成用户数据丢失

在用户 watch 运行期间执行 `init --force`，**把用户正在记录的日志覆盖了**。
之所以没丢，纯粹是因为那个 watch 还在内存里持有旧内容、下一次写回又冲掉了覆盖。
若它当时是崩溃退出，用户的链就永久没了。

**结论：这就是加锁的动机。** 任何会写日志的命令（`init` / `watch` / `announce`）
都必须尊重锁。`announce` 最初漏了，已补。

### 8. 测试命令漏了工作目录 → 在仓库根目录留下文件

有次测试命令没指定 `workdir`，相对路径 `--log audit.json` 跑到了工作区根目录，
建了一批文件；而且"两个进程各锁各的文件"，一度让我误判锁守卫失效，排查了很久。

**结论：测试一律用 `tests/` 下的副本并显式指定工作目录；绝不碰用户正在用的
`audit.json` / `textfile.txt`。**

### 9. 工作区可能被回退 → 交付物要能重建

发生过一次：`交接总结.md` 消失、`README.md` 退回旧版本、`twff/` 与 `demo/`
被移走又移回。所以**交付物必须放在这个目录里、且不依赖目录外的路径**。

**结论：文档里不要写死会失效的相对路径；必须依赖外部仓库的步骤要单独标注清楚。**

## 五、设计取舍（如需改动，先看这里）

| 取舍 | 现状 | 代价 / 备选 |
|---|---|---|
| 变化检测 | 内容 SHA-256 比对 | 同内容不重复记账；改回原样算新事件 |
| diff 算法 | 最长公共前缀/后缀夹逼，O(n) | 片段**不保证落在行/句边界**；要行级对齐需 `difflib.SequenceMatcher`（最坏 O(n²)） |
| 片段存储 | 每段上限 160 字符，首尾保留 | 只存增量，不存全文快照 |
| 内存 | 算 diff 需全文，上限 1,000,000 字符 | 超限时 `diff_truncated=true` 且不猜内容 |
| 预览长度 | 默认 60，**进入哈希** | 是体积主因（preview=300 时占 71.7%）；`init`/`watch` 必须同值 |
| 监视方式 | 轮询（默认 1 s） | 同一间隔内多次修改会合并成一条 |
| 并发 | 锁文件 + 30 s 心跳，90 s 判陈旧 | 探测不可靠时**倾向于拦住** |

## 六、怎么验证改动没搞坏

改任何代码后跑这三步：

```powershell
python test_diff.py                     # 29 项 diff 单测，必须全过
cd tests\5kb
python run_5kb_test.py 60               # 端到端；结束后看 verify 是否通过
python inspect_result.py                # 生成 summary.txt，核对 diff 是否正确
```

**三档对照**（可选，验证体积相关改动）：

```powershell
python run_5kb_test.py 300
python run_5kb_test.py 0
python compare_preview.py
```

> 测试目录里有一份 `chainlog.py` 副本（自包含、可离线复现）。
> **改了主程序记得同步过去**，否则测的是旧代码。
> 另外测试前会清 `audit.json.lock`——上一次被强杀留下的锁在 90 秒内仍会拒绝新 watch。

**跨实现验证**（确认没破坏 TWFF 兼容性）。TWFF 不在本目录内，
把 `TWFF_ROOT` 换成实际位置：

```python
import importlib.util, json, pathlib

TWFF_ROOT = pathlib.Path(r"..\twff")        # 按实际改动
vf_path = TWFF_ROOT / "spec" / "verification" / "verify_process_log.py"

s = importlib.util.spec_from_file_location("vf", vf_path)
vf = importlib.util.module_from_spec(s)
s.loader.exec_module(vf)

log = json.loads(pathlib.Path("audit.json").read_text(encoding="utf-8"))
print(vf.verify_process_log(log))     # 应为 (True, 'Log intact - N events verified.')
```

## 七、已知边界（对外沟通时不要过度声称）

1. **不记录"谁"改的**——只记录文件内容何时变了。
2. **不加密**——`audit.json` 是明文 JSON。目录名里的"encrypt"在本功能中未实现。
3. **重算链无法在链内发现**——攻击者改完重算整条链，链内校验会 PASS。
   必须靠 `anchor.json` 或更强的外部锚定（签名/可信时间戳/服务端）。
   若攻击者能同时改 `audit.json` 和 `anchor.json`，则无从发现。
4. **轮询有粒度**——间隔内的多次修改合并成一条；进程没运行时完全不记录。
5. **diff 不保证语义边界**——见第四节第 5 条与第五节。
6. **未测大文件**——只在 4.75 KB 上做过完整实测。几百 KB / MB 级的行为未验证
   （内存上限、每轮全文读取的开销）。

## 八、下一步建议（按性价比排序）

1. **`preview` 改为"改动位置 ±40 字符的上下文"**
   现在存的是全文前 N 字符。长文档里这一行信息量很低（改在末尾时预览完全不变），
   而它占了 70% 体积。改成围绕改动点的上下文，**同样体积信息量高一个量级**。

2. **接进 Glass Box 编辑器**（补 ProofFlow Demo 缺的那一幕）
   `twff/glassbox/components/process_log.py` 里的 `log_edit()` **定义了但全仓库无人调用**，
   所以"人工输入"从来没被记录。把本功能的 diff 逻辑接进去即可补齐。
   参考：`twff_copy` 与 `twff/glassbox` 的事件格式已经兼容。

3. **大文件压力测试**（500 KB / 5 MB）
   验证 `MAX_TEXT_CHARS` 的降级行为与轮询开销。见第七节第 6 条。

4. **`待办.md` 里的两项**
   - "增加/删除/空闲三种模式，切换时自动保存"——与本功能的 `mode` 字段天然对应。
   - "读取剪贴板，对 copy 进行识别，要求提供类别"——这是新功能，不是本功能的延伸。

5. **数字签名**（把 `anchor.json` 换成真正的锚定）
   这也是 ProofFlow 文档里"有时间再做"的那一层。按本轮的实测，**它不是锦上添花**：
   没有它，"重算链"这种篡改在链内是发现不了的。

## 九、给接手者的三条提醒

1. **先在隔离目录里做实验。** 我调试时因为有次命令漏了工作目录，
   相对路径跑到工作区根目录建了文件；又在用户 watch 运行时 `init --force`
   覆盖了用户的日志。**测试一律用 `tests/` 下的副本，绝不碰用户正在用的
   `audit.json` / `textfile.txt`。**
2. **`--preview-chars` 是哈希输入的一部分。** 改它会让新旧事件哈希口径不一致；
   `init` 与 `watch` 必须同值。
3. **多返回值、三态布尔这类接口，一定要写进 docstring 并有单测。**
   第四节前两条 bug 都是"看起来完全合理"的错误，靠肉眼 review 抓不住。
